### How a request travels through my app

- Uvicorn receives a request through a port and lets it in.
- FastAPI finds the right route (it checks the directory), so it knows what to run.
- Pydantic kicks in to check the shape of the information (it must match RequestAction; if it doesn't, 422 and nothing else happens).
- Depends hands over the tools (provides the database and the notifier).
- The service checks the rules, in order (the office that decides), in Approve(...).execute():
  - Does request 7 exist? If no, 404.
  - Is person 3 the treasurer? (asked through seam.py) If no, 403.
  - Can a request in this state be approved? If no, 409.
  - Is there enough money left? If no, 409.
- If everything passes, it changes the status, writes a row in the history, and saves (commit).
- The notice goes out (the post room): the notifier saves the notice, then the broker puts it only into matching mailboxes, and the requesting rama's open page shows "Your request was approved".
- If anything failed, the service error is raised and the error handler pops up with the right code.
- The answer goes back through uvicorn to the browser, and get_db closes the connection.

uvicorn → route → Pydantic → Depends → service (404 → 403 → 409) → notice → answer, with the error handler catching problems along the way.
